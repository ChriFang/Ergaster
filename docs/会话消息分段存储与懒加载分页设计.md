# 会话消息分段存储与懒加载分页设计

## 1. 背景与目标

当前会话系统存在两个性能瓶颈：

1. 聊天窗口会一次性加载并渲染完整会话消息，长会话下 IPC 传输、React 渲染和滚动布局都会明显变慢。
2. 会话消息全部保存在单个 `messages.json` 中，文件会持续膨胀，每次保存都需要整体重写，不利于后续按页读取和按时间顺序检索。

本次改造目标：

- 将会话消息从单文件改为分段存储。
- 支持按分段懒加载消息页，聊天窗口首次仅显示最近消息。
- 用户滚动到顶部时继续加载更早历史，避免一次性渲染完整会话。
- 保持现有 Agent 对完整上下文和摘要压缩的依赖能力。
- 当前版本未发布，不考虑兼容旧 `messages.json` 结构。

---

## 2. 范围

### 本次实现

- 新建会话目录下的 `segments/` 消息分段结构。
- 后端分页读取会话消息，并按段懒加载。
- 前端聊天窗口首次加载最近 50 条消息，向上滚动继续加载每页 20 条。
- 保存消息时按 1MB 阈值自动切分多个 segment 文件。
- 摘要压缩后重建 segment 文件。

### 本次不实现

- 不兼容旧 `messages.json`。
- 不引入虚拟列表。
- 不做消息全文检索或归档功能。
- 不改造工作流控制台消息分页。

---

## 3. 数据结构设计

### 3.1 会话目录结构

每个会话目录改为：

```text
<conversation-id>/
  meta.json
  segments/
    000001-20260702T021530Z.json
    000002-20260702T033812Z.json
    000003-20260702T054221Z.json
```

### 3.2 segment 文件命名

命名格式：

```text
<6位递增序号>-<UTC时间戳>.json
```

设计理由：

- 序号保证严格顺序，可直接排序。
- 时间戳便于人工排查问题。
- 同秒内多次生成也不会产生排序歧义。

### 3.3 segment 文件内容

每个 segment 文件保存一个 `ChatCompletionApiMessage[]` JSON 数组，示例：

```json
[
  {
    "id": "user-1",
    "role": "user",
    "content": "你好"
  },
  {
    "id": "assistant-1",
    "role": "assistant",
    "content": "你好，请问需要什么帮助？"
  }
]
```

### 3.4 `meta.json` 扩展

建议在 `ConversationMeta` 上新增：

- `storageVersion: 2`
- `segmentCount: number`

其中：

- `messageCount` 表示持久化后的消息总条数。
- `segmentCount` 表示当前 segment 文件数。
- `tokenEstimate` 仍用于摘要触发判断。

## 4. 持久化规则

### 4.1 保留哪些消息

延续当前持久化过滤规则：

- 不保存 `role === 'tool'` 的工具返回消息。
- 不保存带 `tool_calls` 的 assistant 中间消息。

原因：如果只保留 assistant 的 `tool_calls` 而不保留对应 tool 消息，会导致下一次请求模型时出现非法消息链。

### 4.2 segment 切分阈值

```ts
const MESSAGE_SEGMENT_MAX_BYTES = 1024 * 1024; // 1MB
```

切分原则：

- 正常情况下单个 segment 文件尽量不超过 1MB。
- 如果单条消息本身超过 1MB，则允许该 segment 超阈值，但不拆分单条消息。

### 4.3 保存策略

虽然消息存储变成多 segment，但 `setMessages(conversationId, messages)` 仍维持“完整覆盖”的语义：

1. 对完整消息数组执行持久化过滤。
2. 重新切分为多个 segment。
3. 先写入临时目录 `segments.tmp-*`。
4. 写入完成后原子替换原有 `segments/`。
5. 更新 `meta.json`。

这样可以简化摘要压缩、重置会话和一致性处理。

## 5. 后端读取设计

### 5.1 两种读取模式

后端需要同时支持两类读取：

1. **完整读取**：给 Agent 继续对话、摘要压缩使用。
2. **分页读取**：给聊天窗口懒加载显示使用。

### 5.2 完整读取

新增内部方法：

```ts
getAllMessages(conversationId): Promise<ChatCompletionApiMessage[]>
```

职责：

- 顺序读取全部 segment。
- 合并为完整消息数组。
- 过滤非法/不持久化消息。
- 返回给 `AgentService.run` 和摘要逻辑。

### 5.3 分页读取

新增共享类型：

```ts
export type ConversationMessageCursor = {
  segmentIndex: number;
  messageIndex: number;
};

export type ConversationMessagesPageRequest = {
  cursor: ConversationMessageCursor | null;
  limit: number;
};

export type ConversationMessagesPage = {
  messages: AgentMessage[];
  total: number;
  hasMoreBefore: boolean;
  nextCursor: ConversationMessageCursor | null;
};
```

#### 读取语义

- `cursor = null`：从最新消息开始读取。
- `cursor != null`：从当前已加载消息之前继续向前读取更早消息。
- 每次返回的 `messages` 顺序始终是**从早到晚**。

#### 默认页大小

- 首次加载：50 条
- 向上继续加载：20 条
- 后端单次最大限制：100 条

#### 读取算法

1. 加载并排序所有 segment 元信息。
2. 从最后一个 segment 开始逆序遍历。
3. 单个 segment 内从尾部向前取消息。
4. 取够 `limit` 即停止。
5. 将结果反转为正常时间顺序。
6. 返回 `nextCursor`，供下一页继续向前读取。

## 6. 前端分页设计

### 6.1 首次显示策略

聊天窗口首次加载时：

- 只请求最近 50 条消息。
- 默认滚动到底部。

注意：这里不是“最早 50 条”，而是“最近 50 条”，因为用户打开会话时更关心最近上下文。

### 6.2 向上加载历史

当聊天窗口滚动到顶部附近时：

- 如果 `hasMoreBefore === true`
- 且当前没有正在加载旧消息
- 则请求下一页更早消息（20 条）

加载成功后：

- 将旧消息 prepend 到当前消息列表头部。
- 恢复滚动位置，避免视图跳动。

### 6.3 需要新增的前端状态

在 `useChatSession` 中增加：

- `messagesPageCursor`
- `hasMoreMessagesBefore`
- `isInitialMessagesLoading`
- `isLoadingOlderMessages`

### 6.4 滚动恢复

在加载更早消息前记录：

- `previousScrollHeight`
- `previousScrollTop`

prepend 完成后设置：

```ts
container.scrollTop = container.scrollHeight - previousScrollHeight + previousScrollTop;
```

保证视口停留在用户原来看到的位置。

### 6.5 自动滚动到底部

只有以下场景自动滚到底部：

- 首次进入会话
- 切换会话
- 用户发送新消息
- Agent 返回新回复后刷新最新页

加载更早历史时不自动滚到底部。

## 8. 摘要压缩设计

当前摘要逻辑保留，但数据来源改为完整 segment 合并结果：

1. 读取完整消息。
2. 若消息总数大于 `RECENT_MESSAGE_WINDOW`，按规则切分：
   - 旧消息 → 用于生成摘要
   - 最近 6 条 → 保留原文
3. 生成 `summaryMessage`
4. 用 `[summaryMessage, ...recentMessages]` 重建完整消息数组
5. 调用 segment 重写逻辑重新落盘

这样摘要后会自然 compact 掉旧 segment。

## 9. 风险与取舍

### 9.1 风险：Agent 继续对话仍需完整读取

即使前端懒加载，Agent 运行时仍会读取完整持久化历史。这是有意保留的，因为模型上下文需要完整有效历史，摘要机制会负责控制总上下文规模。

### 9.2 风险：保存时重写全部 segment

每次保存会整体重建 segment，不是只追加最后一个 segment。优点是一致性简单，缺点是 IO 成本高于 append-only。当前版本优先选择低复杂度和高一致性。

### 9.3 风险：滚动恢复容易出体验问题

实现时必须明确区分：

- 首次加载
- 加载旧消息
- 收到新消息

否则会出现加载旧消息后被强制滚到底部的 bug。
